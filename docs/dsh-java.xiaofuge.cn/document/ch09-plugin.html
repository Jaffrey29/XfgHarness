第9章 插件开发实战：Java 与 Node 双模式

亲手给系统加一个"天气查询"工具——两种插件模式各写一遍

9.1 本章导读

第8章说了所有工具都穿过统一执行器，那"插件工具"是怎么进来的？本章动手实战：用 Java Native（进程内类隔离）和 Node Bridge（sidecar 进程）两种模式各写一个插件，走通"开发 → 打包 → 安装 → 激活 → 被 Agent 调用"的完整闭环。读完你就能给系统扩展任意能力。

9.2 插件体系的三段式架构

回顾第3章，plugin 域拆成 Registry / Bridge / Runtime 三条边界。从开发者视角，一次插件运行的完整路径是：

💡 关键认知：插件工具没有特权

插件工具注册后与内置工具完全同构——同样过 PRE/POST Hook、同样受超时与重复调用守卫约束、同样产生 ToolCall/ToolResult 事件、同样可被审批矩阵拦截。这就是为什么"唯一入口"（第8章）是扩展性的根基。

9.3 Java Native 模式：写一个天气插件

Java 插件以 JAR 安装，宿主用隔离的 URLClassLoader 加载——插件的类与宿主隔离，插件之间也互相隔离。

9.3.1 五步上手

第1步：引入 types 模块（纯 SPI 契约，不依赖 Spring），继承 AbstractHarnessPlugin：

// plugins/sample-tools-plugin/.../SampleToolsPlugin.java（项目自带示例）
public class SampleToolsPlugin extends AbstractHarnessPlugin {
    public SampleToolsPlugin() {
        super("sample-tools");   // 插件 ID，决定工具名前缀
    }
    @Override
    public List<ToolDefinition> tools() {
        return List.of(new WeatherQueryTool(), new FileSummaryTool());
    }
}

第2步：实现工具，继承 AbstractTool 声明四个要素：

public class WeatherQueryTool extends AbstractTool {
    @Override public String name() { return "weather_query"; }

    @Override public String description() {
        return "查询指定城市的天气信息（温度、天气状况、湿度）。";
    }

    @Override public Map<String, Object> parameters() {
        return objectSchema()
                .prop("city", stringSchema("城市名称，如 北京、上海、深圳"))
                .required("city")
                .build();
    }

    @Override public boolean isConcurrencySafe(Object args) { return true; }  // 只读工具

    @Override public CompletableFuture<ToolExecutionResult> run(ToolRunContext ctx, Object args) {
        // 实际查询逻辑（示例返回模拟数据）
    }
}

name 是调用名，description 和 parameters（JSON Schema）会一起喂给模型——description 写得越清楚，模型越知道何时该调它。isConcurrencySafe 声明无副作用，允许并发。

第3步：在 META-INF/plugin.yaml 声明元数据：

id: sample-tools
name: Sample Tools Plugin
version: 1.0.0
author: Harness Team
description: 示例插件，提供天气查询(weather_query)和文件摘要(file_summary)工具。
entrypoint: cn.walioffice.plugin.sample.SampleToolsPlugin

第4步：SPI 注册——在 META-INF/services/cn.xiaofuge.deepseek.harness.domain.spi.JavaHarnessPlugin 文件中写入入口类全限定名。

第5步：打包成 JAR，放入 harness.extensions.plugins.install-root（默认 ./plugins）。

9.3.2 用 Archetype 快速生成

项目自带 plugins/plugin-archetype，可用 Maven 直接生成插件骨架，省去手写五步。完整命令与 HTTP 安装示例见 docs/java-plugin-development.md。

9.3.3 预置加载（可选）

想让插件随启动自动装载，在 harness.yml 声明 preset：

harness:
  extensions:
    plugins:
      install-root: ./plugins
      node-bridge-enabled: true
      preset:
        - plugin-id: sample-tools
          display-name: Sample Tools Plugin
          plugin-version: 1.0.0
          runtime-type: JAVA_NATIVE
          source-path: ./plugins/sample-tools-plugin-1.0.0.jar
          entrypoint: sample-tools-plugin-1.0.0.jar
          auto-start: true

9.4 Node Bridge 模式：复用 Node 生态

DSH_NODE_BRIDGE 用于跑 Node 插件——宿主启动一个 sidecar 进程（node <entrypoint>），通过 JSON-RPC 通信。

约束与安全边界：

约束说明
入口识别识别 .codex-plugin/plugin.json、package.json、cordis.yml
入口限制必须在插件安装目录内，且是 .js / .mjs / .cjs
进程隔离独立进程，崩溃不拖垮宿主；不经 Shell 拼接避免注入
项目示例plugins/dsh-demo-plugin（已在 yml preset 预置）

9.5 两种模式怎么选

维度Java NativeNode Bridge
性能进程内调用，零 IPC每次调用走 JSON-RPC，有序列化开销
隔离性类隔离（URLClassLoader），但同进程进程隔离，崩溃互不影响
生态Java 生态复用海量 npm 包与既有 Node 插件
依赖仅 JVM需 Node.js 18+
适合高频、性能敏感、企业 Java 团队复用 Node 资产、快速集成第三方

9.6 对话中 @插件提及（v0.1.5 新增）

装好插件后，怎么在对话里显式指定用某个插件？v0.1.5 在控制台引入了 @插件 提及：输入框敲 @ 会弹出已安装且处于 ACTIVE 状态的插件候选（按插件 ID / 显示名模糊匹配，最多 8 条），↑/↓ 移动高亮，Enter/Tab 确认回填 @<pluginId> ，Escape 关闭。

真正的转换发生在用例编排层：AgentDispatchNode 用正则 (?<=^|\s)@([A-Za-z0-9][A-Za-z0-9._-]*) 识别提及（与 pluginId 字符集一致，邮件地址 someone@example.com 不会误判），命中后在消息末尾追加 [插件提及] 指令，要求模型优先在对应 plugin__<插件ID>__<工具名> 工具中选择，其他插件工具只在被指定或确实更匹配时才使用。这样不用切换插件启停状态，就能显式验证某个插件的工具链路。

注意：@插件 提及是优先级引导而非强制路由——模型在工具缺失时仍可能回退到其他插件。提及候选只展示 ACTIVE 插件，DISABLED/FAILED 不出现在补全列表。

9.7 插件接口访问控制（v0.1.5 新增）

插件链路「能装能跑」之后，下一个问题是「谁能装」。v0.1.5 新增 PluginApiAuthFilter（@Order(10)），作用于 /api/harness/plugins 及其子路径：

场景行为
只读请求GET / HEAD / OPTIONS 直接放行（控制台展示不受影响）
本机调用127.0.0.1 / ::1 回环地址放行
远程命令调用必须携带 X-Plugin-Api-Token 头，且与 harness.plugins.api-token 配置一致
鉴权失败返回 401，响应体 {"code":"A0300","info":"plugin API token required","data":null}
 
harness:
  plugins:
    api-token: <your-token>   # 远程调用插件命令接口时必填；为空则远程命令调用一律拒绝

设计取舍：读接口继续开放便于控制台展示；安装、运行、启停、卸载、配置保存等命令接口在远程访问时必须带 Token，避免暴露主机后插件被任意安装或停用。当前 Token 为单值配置，暂不支持多 Token、按插件粒度授权或轮换。

9.8 注册与提示词安全加固（v0.1.5）

9.8.1 pluginId 字符集强制校验

PluginRegistryService 在安装登记时强制校验 pluginId 字符集：[A-Za-z0-9][A-Za-z0-9._-]*——必须以字母或数字开头，只能包含字母、数字、点、下划线和短横线。原因在于 pluginId 会参与注册工具名（plugin__<pluginId>__<toolName>）和安装目录路径拼接，若允许空白、斜杠等字符，会破坏工具命名规则并带来路径穿越风险。非法 ID 在安装阶段直接抛出 IllegalArgumentException，不会写入登记表。

9.8.2 工具注册幂等

PluginToolBridgeService 注册插件工具时改为 putIfAbsent 语义：首次注册正常登记工具名、释放器和提示词区段；重复注册则执行本次产生的所有 disposer、返回已有工具名列表，不再覆盖。避免插件被重复 run 时工具重复挂载、提示词区段重复写入。

9.8.3 提示词注入防护与 Schema 一致

两个配套修正：

修正内容
提示词与 Schema 一致插件能力写入系统提示词时使用注册后的完整工具名（plugin__<pluginId>__<toolName>），而不是插件声明的裸工具名——避免模型按未加前缀的名字调用失败
注入防护插件贡献的工具描述写入系统提示词前经过 sanitizePromptText：换行、回车、制表符统一替换为空格并去首尾空白，防止恶意描述通过换行伪装成提示词结构注入系统提示词

9.8.4 安装脚本加固

scripts/install-plugin.sh 新增 json_escape 处理安装请求字段：反斜杠、双引号转义，多行内容逐行拼接为 \n，行尾多余换行去除。插件 ID、显示名、版本、JAR 路径和入口类名在拼入 JSON 请求体前统一转义，路径中包含空格或特殊字符时不再破坏请求格式。注意：脚本用于远程主机部署时，也必须补充 X-Plugin-Api-Token 请求头。

9.9 验证你的插件

  • ☐ 插件包放入 ./plugins，启动日志出现插件加载记录
  • ☐ GET /api/harness/plugins 能看到插件状态为已激活
  • ☐ 控制台问"北京今天天气怎么样"，Agent 调用了 plugin__sample-tools__weather_query
  • ☐ 工具卡片显示执行结果（SSE step_break → tool_result → done 全链路）
  • ☐ harness_session_event_log 表里有对应的 ToolCall/ToolResult 事件

9.10 小结与下一章预告

本章要点：插件走 install→activate→run 三段，工具注册后与内置工具同构；Java Native 五步（继承 AbstractHarnessPlugin → 实现 AbstractTool → plugin.yaml → SPI 注册 → 打包）；Node Bridge 用 sidecar 进程 + JSON-RPC 复用 npm 生态；选型看性能/隔离/生态三角。v0.1.5 补齐了对话侧 @插件 提及、接口侧 Token 访问控制、注册侧 pluginId 校验与提示词注入防护，把插件链路从「可用」推进到「可信」。
